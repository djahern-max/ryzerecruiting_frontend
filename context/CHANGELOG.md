## AI Usage Metering — chat limit handling, superadmin usage view, and Stripe live-mode go-live (completed 2026-07-28)
Two-part feature landing an AI usage cap end to end. Part one (frontend, this repo, Steps 1–5): the backend's new usage cap returns **429** with `detail: {code: "ai_usage_limit", message: "..."}` instead of 402, specifically so a capped-but-paying tenant is never bounced to the `/upgrade` wall by the existing 402 interceptors. `ChatPage.jsx`'s `sendMessage` (raw `fetch`, per the API-consolidation audit) now checks `data.detail?.code === "ai_usage_limit"` on a non-ok response and appends the backend's message as a normal assistant chat bubble instead of throwing into the red error banner — reusing `IntelligenceMessage` as-is, since a bare `{role, content}` message renders fine with no candidates/meetings. A new superuser-only page, `src/pages/admin/UsageDashboard.jsx` + `.module.css` (routed at `/admin/usage` behind `SuperAdminRoute`, nav entry added next to "DB Explorer" in `AdminHeader.jsx`'s existing `user?.is_superuser` block), fetches `GET /api/billing/usage` via `apiFetch` and renders a per-tenant table — slug, cost, budget, percent bar (amber ≥80%, red ≥100%), event count — plus a grand-total row, with a quiet empty/error state on failure. No tenant-facing meter was built — regular tenant admins see nothing new. Committed as `a15f1cb`.

Part two (ops/config, Step 6, 2026-07-28): moved Stripe from test to live mode and verified the entire subscription lifecycle with a real $20 purchase, refunded after confirmation. No further frontend code changes — Checkout is fully backend-session-driven and a repo-wide grep confirmed no Stripe publishable key exists client-side (the one frontend touch, a price-copy fix in `UpgradePage.jsx` that still showed the old $99 figure, had already shipped as `cc079ad` ahead of this step). Configuration: live $20/mo Price created in the Stripe dashboard (`price_1Ty5C12...`, livemode confirmed via Workbench Inspector); new live-mode webhook destination `ryze-production` → `https://api.ryze.ai/api/billing/webhook` listening on exactly the 3 handled events (`checkout.session.completed`, `customer.subscription.deleted`, `invoice.payment_failed`); server `.env` updated with live `STRIPE_SECRET_KEY`, live `STRIPE_PRICE_ID`, and the live destination's own `STRIPE_WEBHOOK_SECRET` (the classic go-live trap — the test secret would fail signature verification on every live event).

Verification, end to end with real money: unsigned `curl -X POST` to the webhook URL returned 400 "Invalid signature" with the matching WARNING in journalctl, proving DNS/TLS/Nginx/gunicorn/handler wiring before any payment. Full funnel: fresh self-serve signup as Green Path Recruiting → tenant row created correctly → trial expired via SQL → 402 → `/upgrade` wall → live Checkout ($20.00, correct product name, customer_email prefilled) → real card payment → `checkout.session.completed` received, signature verified, tenant activated with `cus_`/`sub_` IDs → confetti page → upgrade wall gone. Cancellation path: immediate cancel + full refund via dashboard credit note → `customer.subscription.deleted` received → tenant set to cancelled. Both webhook handler branches proven in production. Green Path restored post-test to a fresh 30-day trial with Stripe IDs nulled. Backstops set: Anthropic console monthly spend limit $50 (email alert at $30; prepaid balance with auto-reload off is a further hard stop — deliberate tradeoff, revisit when real tenant AI usage grows); OpenAI project spend limit $10 with hard limit enforced (embeddings-only usage; can only trip on a runaway bug, never legitimate volume).
